## 1. 研究真正改变的任务条件

A，§3.1、§4、§8.1：输入是已完成 rehosting fuzzing 后的可复现崩溃测试及对应原始固件二进制，当前实现面向 32 位 ARM Cortex-M。系统重放崩溃，收集执行与访存事件，构建带运行时数据的 use–define 关系，反向污点分析得到候选指令，再给出排序结果供人调查。直接崩溃原因归入非法访存与非法指令执行，以此确定污点汇；直接原因不等于最终根因。输出是定位调查的起点，不是自动修复或取消所有人工判断。

I：最值得写进引言的推进不是“系统有三个模块”，而是把原来昂贵且不确定的历史状态推断，部分变成重放期间实际记录的访存关系，再把可分析的长轨迹变成人能优先调查的短排序。这同时包含两个有区分的价值：可分析范围/效率和调查优先级。记录更多历史使第一项成立，却也可能让候选链更长，因而更需要第二项。§4.3.2 明确把长 UD 链和候选膨胀放在设计之后说明；不应倒写成所有困难都先验独立、每个模块恰好解决一个困难。

A/O：P3 公平介绍三类既有技术：对照测试统计、postmortem 反向分析、学习代码上下文；P4 再指出富调试支持的软件条件与原始固件条件的迁移缺口。这里不是宣称已有方法完全不能定位根因，更不是声称发明反向执行。§6 比较的是作者迁移到 ARM 的 POMP/POMP++；Appendix C 说明共用逆执行 handlers、提供相应格式的 trace 数据、迁移 value-set analysis，并省略 x86 专用启发式。比较支撑其固件实验设置中的效果，不自动证明对所有 fault-localization 家族的普遍优越性。

I：任务价值选择很具体：fuzzing 已经成功留下 crash，却仍有人要查清造成 crash 的指令。把成熟上游的成功作为本文输入，比批评 fuzzing 不够强更准确，也使读者无需相信一个新的安全威胁才认可后续研究。安全后果提供领域价值，崩溃后人工工作提供本任务价值，两者通过“留下测试→理解根因”的操作关系接通。

## 2. 全文读者路径及解释预算

O：全引言从 p.1 右栏起至 p.2 右栏贡献末，约一页多双栏版面；没有独立实验结果段，也没有引言内图例或汇编实例。按本地清理断行后的空白 token 计数，P1–P9 与 B1–B3 共 1123 个 token；计数含引用号、标签与 URL，不是语言学词数或质量指标。逐段记录为 94、96、153、40、134、102、122、186、7、64、43、82。49 个句级单元的逐项分析见配套文件；计数只说明本篇内容分配，不构成新稿配额。

### P1 → P2：先给领域意义，再交出尚未完成的操作

A/O：P1 先定义固件功能，再列制造/医疗等部署，最后用条件背景引出恶意软件、数据窃取和远程控制后果。P2 不停在风险强度：它立即引入 fuzzing 的操作、保存崩溃测试这一输出、发现崩溃仍未结束的转折，以及根因理解的价值。

I：两个段落分别回答“为何在意这些软件”和“已有发现之后还有什么必须做”。功能、使用情境与风险后果共同完成属性→后果→价值的说服路径；关键认知支点却在 P2.S3 的测试保存动作，它让 P3 开头的给定输入自然可得。只保留重要性形容词会丢掉操作链。若面向固件专家，可缩短 P1 定义与行业列举，把篇幅让给迁移条件；代价是一般安全读者更晚知道这类软件为何值得投入。此为 I 的编辑选项，不是对原段价值的否定。

### P3 → P4：先承认强已有答案，再限定可转移条件

A/O：P3 用输入、处理与产物区别三类答案，而不只列研究名。统计路线分为收集测试与计算关联两句；postmortem 和学习路线各用一句，说明本篇后续将使用的 reverse execution / taint 语汇。P4 的让步结构把已有广泛研究保留为事实，把不足落在资源与调试条件变更后。

I：153-token 的综述较长，但承担术语建立和新颖性定位两份工作。先让读者看见已有能力，再说迁移受阻，避免凭空制造“尚无方法”。如果本文只面向 postmortem 专业读者，可缩减三家族综述、增加 POMP 的输入假设与 ARM 迁移问题；能增强近邻辨析，但牺牲 broad audience 的路线地图。原文 underexplored 是范围定位主张，不等同于“第一篇”，也不能作新稿当前新颖性的证明。

### P5 → P7：按任务受阻的位置组织挑战，不按系统模块预留槽位

A/O：P5 先说调查需要理解执行，再指出有用的 trace/register/memory evidence；缺少自动提取机制导致人工检查大量指令；结尾将它归为“提取且利用”运行时证据的挑战。P6 从 stripped binary 的语义缺失走到候选过多，再把旧方法的统一评分/块内不区分落在最终调查指导有限。P7 特意区别两个固件场景挑战之外的共有困难：回溯损坏指针传播时，aliasing 使数据关系不确定。

I：P5 的证据需求在设计之前出现，故后文事件记录不是凭空新增的日志功能；P6 的评分粒度连接人力后果，故 ranking 不是为增加算法点而存在；P7 先讲初始化→调用传播→非法解引用，再定义 alias，读者先理解要追什么，再接受为什么难。三段把技术属性、调查结果与阅读前提一起安排，没有单独的营销或认知口号段。

I：如果合并 P5 与 P7，可沿“缺乏历史观测→逆执行丢失值→别名不确定”形成更紧的一条机制链，减少重复“长 trace 很费时”。代价是淡化作者有意区分的场景基础设施不足与普遍程序分析难题。若把 P7 改成编号 Challenge III，读者易误认为三者同等属于固件特性、并与三个组件一一对应；原文保留共有问题身份更诚实。

### P8 → B1–B3：先解释方案为何成立，再把所得重新归组

A/O：方案独立成段，起于框架与精确目标，然后按 Challenge I、Challenge II、共同 alias 问题逐一接回。顺序为“提出记录→给理由→解释记录对象→引入排序→给理由→返回事件用途”，不是完整实现流水线。末尾没有再插入结果段，直接用一行组织句进入三项贡献。

I：P8 长于任何背景段，因为必须同时让读者相信输入能采、数据有用、候选能排序。若只留下三个模块名称，任务中的两种失败不会自动得到解释。贡献又不是照抄 P8：B1 合并总系统与 event/history 机制，B2 单独保留 analyst guidance，B3 把评价和代码开放合并。这让“可深入分析”与“如何优先看”两项实质所得各有位置，最终再用任务答案收束。

## 3. intuition 与 insight：本篇怎样安排理由

A/O，P8.S4 与 P8.S7：原文分别用 key intuition 标记具体访存能帮助 reverse execution 和 alias resolution，用 key insight 标记 tainted instructions 的根因重要性并不相同。两者都是设计理由，不是前者只能经验猜测、后者必定有先验实验的新颖性分级。P5 开头也用直觉性副词说明调查需要理解 crash，那只是共享前提，不能与技术核心发现混为一谈。

A：§4.1–4.2 把第一理由具体化：action event 记录执行地址，data event 记录实际读写地址与数据；遇到不可逆写寄存器指令时，单靠终态无法还原旧值，而历史访问可恢复相关值，连接不同指令对同一地址的读写。§7 更明确指出传统少记录运行时数据的成本顾虑：记录只在 crash reproduction 阶段进行，因此可花一次局部采集成本换取后续解析节省，并不拖慢整个 fuzzing campaign。

I：更深的可迁移认识是“任务阶段变化会改变值得收集的证据”，并非“日志越多越好”。假设把 P8.S4 改成这个成本/可观测性理由，优势是回答为何旧方法不这样做、为何现在可行；代价是要额外解释 post-fuzzing replay 与在线 fuzzing 的预算差异，不能只替换 intuition 一词就算完成。若篇幅紧，应保留现有具体访问→别名关系，把成本解释留正文。

A：§4.3.2–§6.4 把第二理由细化为两个启发式：重复循环中的计算/复制指令下调，历史上对相关地址写入且离污点汇较远的源指令上调。循环初始化/终止条件与传播中间步骤的调查价值不同。它们是有实证表现和失败例的优先级规则，不是普遍因果定理。

I：引言选择抽象的“重要性不同”能压缩细节且直达人工调查目标，但信息量偏弱。若改成“循环复制反复传播同一错误，而错误写入和边界初始化往往更值得先查”的具体机制句，会更有辨识度；代价是引入循环/历史写两类行为并需要避免把往往写成必然。这个替代改变信息选择，不是同义润色。

O：P8.S6 把评分对象笼统写为所有 instructions；§4.3 与实现说明明确为 backward-tainted set。迁移时应直接写候选/污点指令，以免承诺对全固件每条指令作动态评分。P8.S5 列寄存器和地址，正文 data-event 定义则明确实际读写数据；两处抽象层不同，不能将引言四项当成实现数据结构的穷尽描述。

## 4. 三条贡献各自选择了什么

### B1：系统交付和让长轨迹可处理的关键方法一起说

A/O：三句依次交付固件适配的 postmortem 系统、event-based 方式带来的长轨迹分析能力、具体访存如何解决 alias 并改善效率/效果。作者没有把“实现系统”“收集日志”“解决别名”各拆成独立贡献。

I：这种归组保留同一因果链：更可用的历史证据→逆向分析→长距离定位。读者会把技术方法视作系统价值的根据。若只写平台移植，事件设计与任务改善会被低估；若单列事件采集为新工具，又容易把已有 hooks 当成创新本身。反向执行、Unicorn、Capstone 是论文采用的基础设施；创新主张应落在本场景的证据选择和分析组织，而非发明这些组件。

### B2：把排序转换为调查行动

A/O：第一句有行为分析→给分→注意力分配，第二句将收益落到离 crash site 很远的根因调查。无数值、不新开评价维度，不宣称消除人力。

I：该贡献突出的是最终使用方式，和 B1 的分析可行性不同。它没有用“两种策略”硬拆两个贡献，避免方法数量冒充独立所得。若目标读者关心解释性，仍需区别“有排序的候选指令”与“自然语言因果解释”；后者在 §8.2 是未来方向，不宜随 benefit wording 偷渡进来。

### B3：范围→任务答案→多轴比较→复用入口

A/O：评价条目四句分别给 41 crashes /17 images，38/41 roots in top ten，full-trace completion/效率/top-ten 比较，以及仓库开放链接。它是引言首次出现的定量实验结果；此前“数万条指令”是问题规模描述，不是本文结果。没有单独“我们做了广泛实验”的空泛段，也没有把框架实现替代评价结论。

I：范围信息先出现，让 92.7% 的分母和对象可判断；top ten 把统计数变为人需要调查的候选量，回应 P6。完整轨迹与效率补充解释为什么能查深根因，回应 P5/P7。数值应随证明职责选，而不是认为引言必须堆齐三轴或保留最大的增长比例。source release 作为完成动作放末句，短且可核对；本次只确认论文声明及链接存在于源文，不声称现时仓库状态已核验。

## 5. 正文证据池与应保留的强主张

### 5.1 最强的任务答案及其分母

A/O，§6.1–6.2、表1、Appendix A：研究从公开 Fuzzware 的 61 test suites 中成功复现 41 crashes；这 41 项跨 17 firmware images、20 hardware platforms，包含 C1–C9 synthetic 与 C10–C41 real-world。ground truth 来自已有 crash descriptions 或人工核对汇编/日志。每项 full-trace 分析 timeout 为 48 h；正确指令在前十即成功。FirmRCA 为 38/41＝92.7%，POMP 为 3/41＝7.3%，POMP++ 为 8/41＝19.5%。本分析保留此明确、积极的主结论，不把“不是所有固件”作为每句前置防御语。

I：如果改写末项，优先表述“在41个已复现的评测崩溃中，把38个根因排入前十”，再选择最有解释力的比较。这里 41 是评测 crashes，不能写成发现41个新漏洞、修复38个漏洞或恢复38个固件。61→41 是复现筛选条件，属于评测对象形成过程；若新稿需要论证部署覆盖面，必须显露该筛选，不宜把92.7%理解为对全部61项或所有固件的端到端成功率。

### 5.2 深根因、完整分析与定位成功是三个不同命题

A/O，§6.2、表1：FirmRCA 对全部41项完成 full-trace 分析且没有超时；这不等于全部定位成功。deep 被操作化为根因距 crash site 超过全 trace 长度的50%，11项中10项 top-ten 成功。C12/C13 找到的根因名次为13/21，C32 由于中断上下文恢复事件未采到而找不到适当污点汇。

I：若主卖点是跨很远执行距离的查因，10/11 是比笼统“长轨迹”更对题的补充结果；必须带 deep 的判定条件，不把11当成全数据集。若主卖点是覆盖全轨迹，则先给41/41按时完成，再给38/41正确前十，读者能区分计算可完成与结果有用。这不是削弱主张，而是准确配置两项成功。

### 5.3 两个引言百分比不能直接照搬

O：B3.S3 的 73.2%“更高成功率”对应 38/41−8/41＝30/41≈73.2 个百分点，不是相对提升73.2%。若用相对提升，基于未四舍五入的计数为 (38−8)/8＝375%。迁移表达选百分比点或原始计数最清楚。

O：同句的27.8% full-trace improvement 无法与 §6.2 和表1的完成率对齐。文中报告 FirmRCA 100% 对 POMP++ 73.2%，对应差约26.8个百分点，或按计数 (41−30)/41＝26.829%。不能把原文27.8悄然认证成事实，也不能只替成26.8而不说明这是依据正文核算。用41/41对30/41的完成数可直接表达成立能力。这里记录源内数值不一致，不推断作者错误的原因。

### 5.4 排序消融教会我们选哪个数

A/O，§6.4、图8：四个变体均有38/41 top-ten 成功，但成功集合不同。无排序/仅历史写变体在 C12/C13 为5/5而 C36/C41 为365/481；完整策略在 C12/C13 为13/21而 C36/C41 为1/1。四种同为92.7%不能当作排序增加top-ten总成功率的证据。历史写策略改善15/41项的排名；top-one率为仅历史写73.2%、完整70.7%、无排序与仅循环39%。同一个73.2在此是另一个指标，不应与 B3 的增益混用。

I：B2 讲指导能力，正文最对题的是哪些候选被提到前列、top-one 或逐例排名变化。若为说明完整策略“全面最优”而挑70.7%，会被单策略73.2%反驳；应讲互补成功案例以及取舍。若只写整体38/41，能证明系统有用但解释不了 ranking 的独立价值。

O：§6.4 对 C12/C13 的降级还写平均仅3条；图8两例从5到13、5到21，二例平均增加12个名次。其“平均3”使用何种集合/口径未明确，不能自行补出解释。本次因此不用它支持“代价很小”。这一局部问题不推翻图8清楚显示的 ranking gains 或系统38/41结果。

### 5.5 效率结果与采集成本如何支持取舍

A/O，§6.3–6.5、表2、图7/9、Appendix B/D：全流程效率随分析深度的对比在五个 trace 超过360,000条的样例上做24h timeout 实验，图示增长趋势是经验观察，不能升级成复杂度定理。“polynomial-level acceleration”是原文概括，若用于新写作应优先说同一实验条件下的时间/可完成深度。最后10,000条指令的组件实验中，resolve 均值 POMP 1089.6s、POMP++ 10.5s、FirmRCA <0.01s；它不是所有步骤合计耗时，也不是整个 fuzzing 的速度。

## 6. 保义表达形式与改变内容的方案分开

以下是编辑合成形式，不是论文引文。形式只借用语法关系；不能将示例当成新论文的实验事实。

1. 条件在前、任务在后：在已有可复现崩溃测试的条件下，分析者仍需定位导致崩溃的指令。也可先给主句“分析者需要定位……”，再补“即使 fuzzing 已找到……”。前者把输入作为已知，后者更突出发现之后仍有剩余；不能改成 fuzzing 本身无法有效发现漏洞。
2. 让步定位：已有方法在调试资源充分的软件中取得进展，但原始固件缺少其依赖的信息。也可把原始固件置句首，再用从句承认既有成果。两者保留进展与条件，不能变成前人均无效。
3. 工序加目的：重放时记录具体访存，以恢复逆执行需要的历史关系。也可先写能力“历史访存使……成为可能”，后写系统如何采集。目的式突出作者动作，能力式突出设计根据；须保留重放时可得性。
4. 观察加响应：由于候选指令的调查价值不同，系统按行为分配优先级。也可拆成“候选贡献并不相同。系统因此……”。拆句降低一句承载量，合句把设计因果更紧地保存；“不同”不自动证明任何具体评分规则正确。
5. 结果落对象：在41个评测崩溃中，系统将38个根因排入前十。也可先给比例，再给计数和范围。前者易检查分母，后者先传达总水平；都不能写成定位了92.7%的固件。

改变内容的假设选项已在各段说明：压缩大背景以扩充近邻、把事件理由改成阶段预算取舍、把一般不等重要性改成循环/历史写行为、选择深根因子集或排序消融证明不同所得。它们需要不同事实和篇幅，不能用多几个连接词冒充真正的备选。
